# blast-radius

找出改動在別處會弄壞什麼，在上線前。

改寫自 pstack（poteto）的 blast-radius，拿掉多模型 arena。

**列呼叫端不是重點**，graft callers 一秒就列完。重點是 grep 看不到的壞法。

## 不要相信自己的推論

一篇聽起來對的影響範圍分析沒有價值，不管對不對讀起來都一樣有說服力。所以不要交推論。找出整個安全性依賴的那一兩個事實，跑程式證明。

### 證明到哪一層

每個關鍵事實盡量往下推（越下面越好），並寫出停在哪一層：

1. 只是說說。單獨不算數。
2. 指出那一行。真實的 `file:line`，或套件自己的原始碼。
3. 一步步推演壞情況不會發生。
4. **跑過了。** 腳本或測試呼叫真實程式碼，你錯了它會大聲失敗。
5. 在執行中的 app 重現。

第 4 層通常就是一支小腳本：import app 實際用的同一個套件或模組，呼叫你擔心的那個函式。

## 步驟

1. **讀改動。** 預設範圍是 `git diff`（含未 commit），使用者指定的檔案、commit 或分支優先。列出新增、修改、刪除的符號，以及它**現在行為上有什麼不同**，包括 diff 沒寫明的部分。
2. **找出它安全的那一個事實。** 多數看起來危險的改動，安全是因為單一事實，例如「新參數有預設值，舊呼叫端行為不變」「這個呼叫只清掉已經失效的快取」。找到它。它成立的話，大部分疑慮一次清掉。時間花在這裡，不要列一長串「可能」。
3. **看 grep 停下的地方。** 讀你呼叫的套件原始碼，確認鎖定的版本和本地 patch。弄清楚執行時機：非同步、事件順序、頁面卸載、快取。追符號搜尋找不到的東西：API 回傳的 JSON、資料檔格式（例如 `data/*.js`、`*.json`）、部署白名單、另一種語言讀同一份資料、URL 參數、localStorage key、三層之外的下游。
4. **誠實評估每個風險。** 給它真實的發生機率和真實的代價。確認過的風險留著；檢查後排除的另外列。引用真實 `file:line`；搜尋找不到東西也是答案。絕不編造呼叫端或 API。
5. **證明那個事實。** 寫腳本或測試跑真實程式碼（放 scratchpad），執行，貼上結果。

## 交回的內容

- **它做了什麼。** 改了什麼，包括不明顯的部分。
- **它安全的那個事實。** 寫出事實、停在第幾層、證明（腳本路徑與輸出）。證明不了就寫「未證明」。
- **風險。** 每個寫：怎麼壞、`file:line`、機率與嚴重度、怎麼檢查。重要的附證明。
- **已排除。** 檢查過什麼、為什麼沒事。
- **合併／部署前。** 能抓到真實 bug 的最便宜測試或重現步驟，附你寫的腳本。

只讀不改：發現問題只回報，不自己修。
