# correct

使用者在這個 repo 一再糾正 agent 同樣的錯。改 repo，讓下一個 agent 犯不了。

改寫自 pstack（poteto）的 correct。

假設每個貢獻者都是 agent：只看到自己打開的檔案、照抄最近的範例、走最短能跑的路。把 repo 設計成「從一個檔案看起來對的改動，對整個 repo 也是對的」。

## 1. 找出錯誤類型

讀這些來源，把錯誤分類。**同一類發生兩次才算數。**

- 最近的 commit、revert、修正型 commit（`git log --oneline -100`，找 fix、revert、again、missed）
- `AGENTS.md`／`CLAUDE.md`、LESSON 檔、`docs/` 裡的規則
- Claude Code 自動記憶：`~/.claude/projects/<專案 slug>/memory/` 的 feedback 與 project 類記憶。**這是最集中的「被糾正過」紀錄。**
- 解釋 workaround 的註解

使用者指定了錯誤類型時，只處理那一類。

## 2. 每一類在能用的最高層解決

1. **用架構消除。** 每份狀態只有一個擁有者，每件事只有一種做法。藏起內部，讓錯的 import 直接失敗。手動同步的清單改成單一來源自動產生（例如部署白名單改成從目錄產生）。刪掉 agent 會照抄的舊做法和死碼。
2. **用型別讓壞狀態寫不出來。** 壞程式碼還是能過時，加 lint 或檢查腳本，**錯誤訊息要點名該用的檔案、型別或函式**。這個壞模式已經很普遍時，只在改動新增時失敗。
3. **測試行為。** 修掉或刪掉「行為壞了還會過」或「只改內部就會失敗」的測試。
4. **最後才寫文件或 agent 規則**，只用在需要判斷的事。agent 跳過文件時什麼都不會失敗。

## 3. 修並證明

一次修最常發生的那幾類，每類一個獨立改動。**證明每個新檢查會在一次真實發生過的錯上失敗**：checkout 那個出錯的 commit（或還原那段錯誤），跑檢查，貼出失敗輸出。本機和 CI／部署腳本跑同一個指令。

例外要寫在出問題的那一行上，附理由、到期日、使用者核准。

依使用者的流程：改完先讓使用者驗證，不要自己 commit 或 push。

## 4. 維護規則表

在 agent 指令檔（`AGENTS.md` 或 `CLAUDE.md`）維護一張表，每條規則對應強制它的東西：

| 規則 | 強制方式 |
|---|---|
| <規則> | <檢查腳本／型別／測試路徑，或「僅文件」> |

之後使用者再糾正時：修掉錯，加規則。如果規則早就在、只是沒有東西強制，那就是重犯，在同一個改動裡用最高層解決。錯誤不可能再發生時，就刪掉那條規則和對應記憶。

## 回覆

每一類寫：證據（commit、記憶檔、規則出處）、選了哪一層、為什麼更高的層不行、新檢查在真實錯誤上的失敗輸出。
