# why

**從紀錄回答，不從程式碼猜。** 程式碼只說明「現在是什麼」，不說明「為什麼」。

改寫自 pstack（poteto）的 why。

## 步驟

1. 定位對象：用 graft 或 grep 找到檔案與行號。範圍不清楚時，先說出你的理解再查，使用者可以修正。
2. 找出引入它的 commit 與之後每次修改：
   - `git log -L <起>,<終>:<檔案>`：追一段程式的完整變更史
   - `git log -S '<字串>' --oneline`：找某個字串第一次出現與被移除的 commit
   - `git blame -w -C <檔案>`：找每一行最後一次修改，再往前追
3. 讀每個關鍵 commit 的完整訊息（`git show <sha> --stat`），以及它連到的 PR、issue（`gh pr view`、`gh issue view`，有 GitHub remote 時）。commit 訊息裡的 FI 編號、bug 編號，要去 vault 或 `docs/` 找對應的詳細檔與判定歷程。
4. 紀錄不夠時再看其他來源：`docs/`、plan 檔、`AGENTS.md`／`CLAUDE.md`、LESSON 檔、旁邊的註解。

## 回答

- 先用一兩句講結論。
- 每個理由都附出處（commit SHA、PR 編號、檔案路徑），**引用作者原話**。
- 自己推出來的部分明確標「推論」，不要和紀錄混在一起。
- 最後寫「紀錄沒回答的部分」：哪些問題查不到答案。查不到也是答案，不要編。

## 不要做的事

- 只看現在的程式碼就說明動機
- 把推論寫成事實
- 順手改程式碼
