# 設計紅旗

每個候選形狀都先用這份篩。命中一條就是修改或否決的理由。

假設下一個改這段程式的是 agent：它只看它開過的檔案、照抄最近的範例、走最短能 compile 的路。偏好「只看一個檔案改對了，整個 repo 也就對了」的設計。

## 淺模組
介面大、藏的東西少。呼叫端要按順序呼叫好幾個函式才完成一件事，或選項暴露內部階段。→ 合成一個介面小、背後做比較多事的模組。

## 資訊外洩
同一個內部決定（格式、公式、key 命名、wire 型別）出現在兩個以上模組，改一處要同步改多處。→ 外部資料在邊界轉成內部型別，格式細節只留在一處。

## 依時間切模組
照執行順序切（load／validate／transform／save 各一個檔），結果同一個資料表示和不變條件在每一層重複一次。→ 依「誰擁有這份知識」切。

## 傳遞函式
只是把同樣參數轉給另一個同形狀的函式，沒有增加任何政策或轉換。→ 刪掉，或讓真正能完成工作的模組負責。

## 分裂擁有權
兩個以上模組寫同一份 state，或各自留一份副本。→ 每份 state 只有一個擁有者，其他人讀或請它改。

## 同一件事兩種做法
新做法和舊做法並存，agent 先找到哪個就抄哪個，兩邊都會繼續長。→ 只留一種，同一次改動把呼叫端搬過去並刪掉舊的。

## 手動同步的清單
兩處以上列同一組項目，加一項要改每個地方。→ 只留一份，其他從它推導；推導不了就讓 build／測試在不一致時失敗。

## 前後端各算一次
同一個公式在 TS 和 Python 各寫一份。→ 能只算一邊就只算一邊；必須兩邊都有時，plan 要有 parity 驗證步驟（同輸入比對輸出）。
