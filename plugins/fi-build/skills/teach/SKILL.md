# teach

**說清楚它是什麼、怎麼運作、為什麼這樣設計，用一篇白話說明，照使用者的步調。目標是讓他懂，不是改東西。**

改寫自 pstack（poteto）的 teach。

## 步驟

1. **決定他該帶走哪幾件事。** 從對話看出他為什麼問（要改它、要 review、在 debug、剛接觸）和他已經懂什麼，不要用問題考他。已經懂的跳過，深度放在他問的地方。
2. **讓 how 和 why 去挖，不要自己重做。** 先自己讀一下程式碼找方向，再呼叫 `fi-build:how` 和 `fi-build:why`（Skill tool），能平行就平行，再合併結果。大小配合問題：子系統兩個都跑，小改動可能一個就夠。why 的保留語氣（「推論」「紀錄沒說」）是發現，不是文風，**原樣保留**。
3. **先給白話定義。** 說出它的名字和一般意義，像資深工程師口頭解釋那樣，有通用名稱就講出來。再接到眼前的案例（「在這個專案裡，我們用它來…」），然後往下：怎麼運作、背後的理由、邊界情況。每一部分都講它解決什麼問題、實際怎麼做到。列函式和常數是參考資料，不是教學。
4. **先給最小的完整答案，一兩句，然後停。** 他追問再加層次。絕不丟一整面文字牆。
5. **是對話，不是演講。** 問他要深入還是往下走，跟著他的方向。不出測驗、不要他複述、不寫「重點來了」「這裡比較難」「關鍵在於」「TL;DR」這種標籤句，直接講。沒有人即時回應時（一次性輸出），完整講完，最後才問要不要深入。
6. **能給看就給看，圖要一張一張疊。** 最快的方式是打開 diff 或程式碼時就打開。三個以上的部件時，不要一張圖畫完全部；畫一系列，每張重畫上一張再加一個部件，讓讀者看著系統組起來。例如 A→B→C 的流程畫三次：先 A→B，再加 C，再加回傳線。流程和結構用 Mermaid；空間性的東西（版面、重疊、捲動位置、前後對照）用 ASCII 示意圖。單一簡單概念不需要圖。

## 寫法

- 繁體中文，像跟同事口頭解釋。精簡但不省略讓人「懂了」的那一句。
- 講具體機制，不用比喻、不先預告接下來要講什麼。目標密度範例：「虛擬捲動分兩部分，一個負責渲染，一個負責從磁碟載入。項目捲出緩衝區時，它的 DOM 節點和記憶體資料都會被清掉。」
- 句子短。子句堆起來就拆成兩句。
- 每個概念只取一個名字，從頭用到尾。
- 這些步驟是給你的指示，不是要印出來的標題。

## 回覆

就是說明本身，不是「我做了什麼」的報告。先講主旨，再講它是什麼、怎麼運作、為什麼，最後列出值得用 how 或 why 繼續追的線索。
