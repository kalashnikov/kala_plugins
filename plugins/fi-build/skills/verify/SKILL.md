# fi-build verify

證明 FI 真的做好了。**檢查真實的東西，不檢查替代品**：不靠「compile 過」「agent 說做好了」「檔案時間有更新」「之前的截圖」。

改寫自 pstack（poteto）的 prove-it-works、blast-radius、explain-the-number、benchmark-checklist。

## 0. 收集對象

1. 讀 FI 的 vault 條目、詳細檔，以及 plan（vault 備註或詳細檔 `判定歷程` 連到的 plan 檔）。沒有 plan 也可以跑，用 FI 描述當驗收標準，並在報告註明「無 plan」。
2. 找出這次的改動：`git status`、`git diff`，以及 FI 開工後的 commit（`git log --oneline` 找 FI 編號或 plan 時間之後的 commit）。列出改了哪些檔、新增或改了哪些函式與元件。
3. 讀專案 `AGENTS.md`／`CLAUDE.md` 的驗證段落，找出專案自己的驗證指令（例如 `pnpm verify`）與前端實測方式（例如 headless chrome、dev server 規定）。**照專案規則跑**，例如規定 repo 內不准跑 dev server 就不跑。

開 todo：每個 plan 步驟的 Verify 一項，再加：靜態檢查、影響範圍、數字（有的話）、報告。

## 1. 靜態檢查

跑專案的單一驗證入口（測試＋型別＋lint）。失敗就記錄原文；不是這次改動造成的失敗要用 `git stash` 或對照 main 證明，不能只說「既有問題」。

這一關過了**不等於**完成，只是入場券。

## 2. 在真實對象上驗證

逐一做 plan 每一步的 **Verify**（沒有 plan 就依 FI 描述自訂 3–6 項）。對象依改動種類：

| 改動 | 真實對象 | 不算數 |
|---|---|---|
| 前端頁面／元件 | 實際打開頁面操作，截圖存 scratchpad，讀 console error | 看程式碼覺得對 |
| API route | 對執行中的 server 打 request，看實際 JSON | 只看型別 |
| 計算／公式 | 用真實資料跑一次，對照一個手算或獨立算法的值 | 單元測試 mock 的值 |
| 排程／腳本 | 實際跑一次（或 dry-run），看輸出與寫入的 key／列 | 看 crontab 有寫 |
| production 上線後 | 正式網域實際操作 | 本機成功 |

規則：

- 驗證失敗時，**先懷疑觀察方法**（快取、看錯環境、舊 build），確認後才判定系統錯。
- 能寫成腳本就寫成腳本，讓下次可以重跑；腳本放 scratchpad，值得留的才建議進 repo。
- 沒辦法在真實對象驗的項目（例如要等收盤後資料、要正式部署），標「沒驗」並寫什麼時候、怎麼驗。

## 3. 影響範圍（改到共用模組時必做）

改動碰到不只一個呼叫端的函式、型別、Redis key、API 回傳格式、CSS token 時才做。

1. 列呼叫端（graft callers／grep），**但列清單不是重點**。
2. 找出「這次改動安全，是因為 ___」那一個關鍵事實。例如「新參數有預設值，舊呼叫端行為不變」。
3. 看 grep 看不到的地方：別的 repo 或 Python 讀同一個 key、iOS app 讀同一個 API、快取裡的舊格式資料、套件 patch。
4. 把關鍵事實推到下面的層級，越下面越好，並寫出停在哪一層：
   1. 只是說說 — 不算數
   2. 指出 `file:line`
   3. 一步步推演壞情況不會發生
   4. **寫腳本或測試呼叫真實程式，錯了會大聲失敗**
   5. 在執行中的 app 重現
5. 做不到第 4 層就在報告寫「未證明」。

## 4. 數字（有量到數字才做）

回測結果、績效、速度、筆數覆蓋率等任何要拿來報告或做決定的數字，過 [`references/number-checklist.md`](references/number-checklist.md)。沒過的數字在報告標「不確定」並寫缺哪一題。

## 5. 報告

先寫結論：**通過**、**有項目沒過**、或**部分沒驗**。

證據表：

| # | 項目 | 結果 | 依據 | 證據 |
|---|---|---|---|---|
| 1 | <plan 步驟 Verify 或自訂項> | ✅／❌／⏸ 沒驗 | 實測／推論 | <指令輸出摘要、截圖路徑、`file:line`> |

接著：

- **影響範圍**：關鍵事實＋停在第幾層＋證明（腳本路徑與輸出）。沒做就寫原因。
- **數字**：每個數字附次數、範圍、限制因素；沒過檢查的標不確定。
- **沒過的項目**：原文錯誤、推測原因（標「推測」）、建議修法。**不自己動手修**，等使用者決定。
- **沒驗的項目**：什麼時候、怎麼驗。

全部通過時最後一句：「可以跑 post-impl 與部署流程；上線確認後 `/feature-ideation archive FI-NNN`。」

## 不要做的事

- 用「compile 過」「測試綠了」當完成
- 把推論寫成實測
- 驗證中途順手改程式碼（即使很小）
- 交給使用者一個你自己能跑的檢查
- 部署、寫正式 DB、動排程（驗證只讀；需要時請使用者授權）
