# 數字檢查表

要報告或拿來做決定的數字，先把下面要說的那句話寫出來（例如「新公式順時針比例 57%，舊的 36%，20 檔 2 年日資料」），再用七題檢查它。每題用跑出來的證據回答，不用讀程式碼的猜測。

只要粗估時跑一次就好，但第 4、7 題還是要檢查，並說明「只跑一次」。在兩個方案之間做選擇時，不算粗估。

1. **為什麼不是兩倍好（或兩倍差）？** 說出限制這個數字的東西：資料深度、樣本數、API 速率、單核 CPU、快取。說不出來，就不知道自己量了什麼。
2. **兩邊條件一樣嗎？** 新舊方案要用同一份資料、同一個區間、同一個 universe、同樣的成本假設，並且都是正式環境的設定（production build、真實快取狀態）。一邊用預設值時，比的是設定，不是做法。
3. **有沒有超出可能的範圍？** 算一下上限：拿掉一個占 10% 時間的步驟，最多快約 11%。報酬、勝率、覆蓋率好得不合理，通常是快取、沒跑到、或 bug。
4. **有沒有錯誤？** 數失敗、空值、NaN、被跳過的 ticker、非 200 回應。輸出要對，不是只有「有東西」。腳本沒數錯誤就加上去。
5. **能重現嗎？** 速度類至少每邊跑 5 次、交錯跑（A、B、A、B），報中位數與範圍。差距小於每次的變動，就是沒有差。回測類要固定資料快照與參數，寫出重跑指令。
6. **對使用者有意義嗎？** 局部變快時，要量使用者實際等待的整段時間。統計上顯著時，要問決策會不會因此改變。
7. **工作真的有發生嗎？** 確認計算真的在量測範圍內跑了：資料真的抓到、列真的寫入、結果真的被使用。逾時、快取命中、沒被 await 的 promise 都會產生「數字」。

**金融數字另外三題**（專案不變條件要求時必答）：

- **point-in-time**：每個時點只用當時以前的資料嗎？有沒有用到事後才公布或事後修正的值（還原權值、財報修正、現存名單造成的倖存者偏差）？
- **交易成本**：含手續費、滑價嗎？假設寫出來了嗎？
- **可重現**：資料來源、區間、git SHA、參數有記下來嗎？

## 報告格式

- 先寫判定：較好、較差、沒有可量測的差異、或不確定。
- 數字附單位、次數、範圍、限制因素。例如「中位數 41 ms → 33 ms，每邊 7 次，之後範圍 32–35 ms，卡在單核 JSON 解析」。
- 說不出限制因素、一邊沒調好、或第 4、7 題沒檢查時，判定是「不確定」，並寫出缺什麼。
