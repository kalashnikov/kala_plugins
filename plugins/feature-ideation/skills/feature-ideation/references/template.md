# vault 範本

新建 `docs/feature-ideas.md`（或使用者指定的路徑）時的樣板。`<...>` 依專案填入。
**不存在的路徑不要寫進分工表**（會變成壞連結）。

格式同時也是 `check` 的統計契約。擅自改裝飾或標題，計數和到期偵測就會壞掉。
契約一覽見本檔末尾「與 check 的契約」。

---

````markdown
---
title: "<Project> Feature Ideas"
last_sweep: YYYY-MM-DD   # 全部列都與實作狀態（程式碼 / CHANGELOG / 外部規格）核對過的最後日期
---

# <Project> Feature Ideas

之後想評估的改善候選 **vault**。依效益、難度、限制相容性判斷優先度，
動工的項目移到末尾的紀錄表。**這個檔案不放實作計畫**（→ 分工表）。

**專案不變條件**: <用 1〜3 行寫 value prop / 非目標。例：「在 Markdown 目錄放一個執行檔就能 RAG 化」＝ 不增加外部 runtime 依賴>
會破壞這些條件的候選，限制標為 `⚠️` / `❌`。

## 與既有文件的分工

| 路徑 | 角色 | 與 vault 的關係 |
|---|---|---|
| `<docs/feature-ideas.md>`（本檔） | 點子 index + 2 張紀錄表 | — |
| `<docs/feature-ideas/>FI-NNN*.md` | 個別點子的**詳細檔**（論點、採用條件、判定歷程） | 從備註連結 |
| `<docs/plans/>` | **實作計畫** | 不放進 vault 目錄。從備註連結 |
| `<docs/specs/>` | 規格調查、需求（含附取得日期的外部規格） | 同上 |
| `<docs/decisions/>` | ADR（決策的固定紀錄） | 從紀錄表的 `證據` 連結 |
| `<docs/known-issues.md>` | **有觸發條件的遺留事項**（「出現實害時」「有人要求時」）的固定位置 | 移出 vault |
| `<TODO.md / CHANGELOG.md>` | 已實作的歷史 | 不與已實作紀錄重複管理 |

## 圖例

| 欄 | 值 | 意義 |
|---|---|---|
| ID | `FI-001` | 與類別無關的流水號。**編了就不改**（紀錄表、ADR 會引用的外部鍵） |
| （遷移時） | `id_style: categorical` | 寫在 frontmatter 就能直接統計 `A-1` 形式的 ID。用於不改 ID 遷移既有 vault（見後文） |
| 狀態 | `idea` | 已登錄、未動工（預設值） |
| 狀態 | `probing` | 深入研究中。有詳細檔，尚未決定採用與否 |
| 狀態 | `planned` | 已寫 spec / plan，交給實作流程 |
| 狀態 | `frozen` | 等待觸發條件。沒有期限（不是我方能判斷的） |
| 效益 | 大 / 中 / 小 | 大 = 核心指標有數字變化 / 中 = 痛點減少 / 小 = 有了方便 |
| 難度 | 低 / 中 / 高 / 極高 | 低 = 半天〜1 天 / 中 = 數天 / 高 = 1〜2 週 / 極高 = 以月計、侵入既有架構 |
| 限制 | ✅ / ⚠️ / ❌ | 是否破壞專案不變條件。`⚠️` **一定要在備註寫升級條件** |
| （選用）依賴 | 套件 / 服務 | 只有「新增依賴與否」是採用首要標準的專案，才加第 8 欄 |

**書寫規範**（一旦走樣，`check` 的統計就會壞）

- 狀態**不加裝飾**，只寫上面 4 個詞（不要寫成 `**done**`、`✅ done`）
- `done` / `declined` 不留在 index。**整行移到紀錄表**（不留墓碑行。ID 的缺號由 2 張紀錄表解釋）
- 備註 **200 字以內**。超過就升級為詳細檔，備註改成「一行摘要 + 連結」
- **有日期的追加內容寫到詳細檔的 `## 判定歷程`，不要堆在備註**
- 不要「一行多個項目」。只完成一部分時，把完成的移到紀錄表，**剩餘部分開新 ID**
- 若採用 `依賴` 欄，所有類別表都要統一。**不要超過 8 欄**

## 重新評估佇列

**只放能寫成日期的**。只有「出現〜時」「驗證〜之後」這類觸發條件的，
不放 vault，放 `<known-issues.md>`（見更新規則 6）。

| 期限 | ID | 要判定什麼 | 判定依據 |
|---|---|---|---|
| YYYY-MM-DD | FI-002 | <例：前處理走 hook 後能否升為 ✅> | <例：2 週份的 trial-log> |

- `期限` 只寫 `YYYY-MM-DD`。不寫相對說法（「2〜3 週後」），也不寫條件句
- **`要判定什麼` 不可留空**。只有日期的期限，到了那天也不知道要決定什麼，就會爛掉
- 判定後**刪除該行**，結論帶日期寫進詳細檔的 `## 判定歷程`

## 優先挑選 (YYYY-MM-DD 版)

**「接下來要動手的話」個人押注順序**

1. **FI-00N (名稱)** — 一句話理由（為什麼是這個順序）
2. **FI-00M + FI-00K (組合名)** — 可一起處理的輕量功能組
3. ...

**刻意延後**

- **FI-00X (名稱)** — 理由（YAGNI / 回報太薄 / 等基礎 X 完成 等）

**改選觸發條件**（任一成立就重選。`check` 會偵測並提議）

- **T1** 距上次挑選已 **90 天**
- **T2** 挑選項目**過半**已 done / declined
- **T3** 上次挑選後新增了 **10 項以上**點子
- **T4** **不在挑選中的 ID 進了已實作紀錄**（代表挑選已偏離實況）

> 內文**只保留最近 2 版**。更早的可刪（完成項目以已實作紀錄為準）。

## 已實作紀錄

已實作、已出貨的候選。詳細經過以連結目標為準。

| ID | 名稱 | 完成日 | 證據 | 心得 |
|---|---|---|---|---|
| FI-00N | <名稱> | YYYY-MM-DD | <PR #123 / v0.12.0 / ADR-0004 至少一項> | <連到詳細檔或知識筆記，或一行學到的事> |

- **`證據` 不可留空**。PR 編號 / tag・版本 / commit / ADR 至少一項。
  決策被推翻或含不可逆決定時，也附上 ADR
- **`心得` 不可留空**。用一行寫實作中學到的事（特別是**登錄時的預想哪裡錯了**），
  或連到詳細檔、知識筆記。這欄沒填，實作得到的知識就不會回到 vault。
  **從既有 vault 遷移過來的行不受此限**（當時可能沒留下心得）。
  不可留空只適用遷移後新增的行
- 新行**加在最上面**（完成日降冪）

## 不採用紀錄

放棄的候選。**符合復活條件就可以移回對應類別表**。不做實體刪除（省下重複討論）。

| ID | 名稱 | 判定日 | 理由 | 復活條件 |
|---|---|---|---|---|
| FI-00M | <名稱> | YYYY-MM-DD | <為何放棄。合併時寫「合併：與 FI-0NN 重複，出處移到 FI-0NN 備註」> | <發生什麼就移回。沒可能就寫 `—`> |

- 重複 / 別名 / 併入上位項目也用這張表（不開第 3 張表）
- 2 張紀錄表合計超過 **60 行**，就按年切到 `<feature-ideas/>archive-<年>.md`

## 更新規則

1. 新點子可以先自由寫在**待整理**區。ID 之後再編
2. 到「可能會做」的階段就編 ID 放進類別表（狀態 `idea`）。
   **下一個 ID = max(index + 2 張紀錄表) + 1**。缺號不重複使用
3. 備註超過 200 字 / 需要論點、URL、程式片段 → 升級為 `<feature-ideas/>FI-NNN.md`，狀態改 `probing`。
   備註換成「一行摘要 + 連結」。**評價變動時的帶日期追加寫到詳細檔的 `## 判定歷程`**
4. `<feature-ideas/>` 底下的檔名**必須以 `FI-` 或 `archive-` 開頭**。
   實作計畫放 `<docs/plans/>`，規格調查放 `<docs/specs/>`，ADR 放 `<docs/decisions/>`
5. **不要產生孤兒** — `<feature-ideas/>` 的每個檔案至少要被 index 或其他詳細檔連結一次
6. 重新評估時間**自己能決定**的，用日期寫進重新評估佇列。
   **要等外部條件的，移出 vault 放到 `<known-issues.md>`**（真的移不出去才以狀態 `frozen` 保留）
7. 實作、出貨後**整行移到已實作紀錄**；放棄則**整行移到不採用紀錄**
8. 盤點過某類別，就更新該類別的 `最後確認`。**只有全部列都核對過時**才更新 frontmatter 的 `last_sweep`
9. 以外部平台（其他工具的功能等）為前提的行，每次盤點都重查官方文件
10. 更新 vault 後，在末尾**變更紀錄**加一行

---

## 待整理

- _（編 ID 前的點子自由寫在這裡）_

---

## 變更紀錄

<vault 自己的更新日誌。一個 session 一行，新的在上。「最近動了什麼」看這裡>

- **YYYY-MM-DD**: <例：全部盤點。5 項 done 移到紀錄表，2 項合併移到不採用紀錄。拆掉 1 個類別>
- **YYYY-MM-DD**: <例：新增 FI-045〜FI-052（UX 小改類別）>
````

## 與 check 的契約

範本中「禁止裝飾」「標題格式固定」，都是為了讓 `check` 能機械式統計。
以下區分各專案可以改動和不能改動的部分。

| # | 契約（不能改） | 格式 |
|---|---|---|
| 1 | ID | `FI-` + 3 位數字（`id_style: categorical` 時為英文 1〜2 字 + `-` + 數字） |
| 2 | index 的狀態 | 只能是 `idea` / `probing` / `planned` / `frozen`（不加裝飾） |
| 3 | vault 整體盤點日 | frontmatter `last_sweep: YYYY-MM-DD` |
| 4 | 類別確認日 | 類別標題正下方的斜體行寫 `最後確認 YYYY-MM-DD` |
| 5 | 項目最後更新 | 詳細檔 frontmatter `updated:` 與檔案實際 mtime |
| 6 | 期限 | `## 重新評估佇列` 表的 `期限` 欄（只能 `YYYY-MM-DD`） |
| 7 | 挑選改版日 | 標題 `## 優先挑選 (YYYY-MM-DD 版)` |
| 8 | 紀錄表 | `## 已實作紀錄` = 5 欄（`證據` / `心得` 非空），`## 不採用紀錄` = 5 欄 |
| 9 | 詳細檔目錄 | 底下只能有 `FI-NNN...` 或 `archive-YYYY...`（categorical 則為 `A-9...` 等） |

可以改動的部分：類別的數量、名稱、順序，`依賴` 欄有無，備註寫法，專案不變條件的寫法。

**以下區段標題必須逐字使用**（`check` 靠它辨識區段，後面可以接括號或日期）：
`## 與既有文件的分工`、`## 圖例`、`## 重新評估佇列`、`## 優先挑選`、`## 已實作紀錄`、`## 不採用紀錄`、
`## 更新規則`、`## 待整理`、`## 變更紀錄`。其他 `## ` 標題一律視為類別。

## 從既有 vault 遷移（`id_style`）

舊格式 vault 的 ID 常依類別編（`A-1` / `C-7` 等）。
改成 `FI-NNN` 才是正規做法，但 **ID 是被紀錄表、ADR、知識筆記、程式碼 doc 註解引用的外部鍵**，
實際運作的 vault 改 ID 可能要動數百處，而且同樣寫法可能和別的命名空間（spec 的設計決策 ID、audit 的指摘 ID）衝突。

因此在 frontmatter 寫下面這行，**就能不改 ID 直接統計**。

```yaml
---
title: "<Project> Feature Ideas"
id_style: categorical
last_sweep: YYYY-MM-DD
---
```

- 詳細檔命名規則也跟著變成 `A-9-...md`
- 外部引用偵測也用同樣格式（只抓有 `feature-idea` 修飾的規則不變）
- 沒宣告卻有 `A-1` 形式的行時，會警告這些行未被統計並說明宣告方式

**新建的 vault 不要用。** 類別重組造成 ID 與類別不一致的問題，只有 `FI-NNN` 能解決。

`check` 讀表頭依欄名決定位置，所以**欄位順序不同也能動**。
但欄名（`ID` / `狀態` / `名稱` / `效益` / `難度` / `限制` / `備註`）不要改。
