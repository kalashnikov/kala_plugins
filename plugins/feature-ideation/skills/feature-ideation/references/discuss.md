# discuss — 深入研究一個既有點子

用 `/feature-ideation discuss FI-012` 啟動。對 vault 中的一項以問答方式深入，
結果以「更新行內備註」或「升級為詳細檔」的方式保存。

## 步驟

### 1. 確定對象

Read vault index，找該 ID 的行。找不到就說
「ID `FI-012` 不在 vault 中。請用 `/feature-ideation:check` 看清單，或不帶參數啟動來新增」
並**中止**（不要擅自選相似的 ID）。

若有詳細檔（`<feature-ideas>/FI-012*.md`）就 Read。檔名不一定是 `FI-012.md`，
要用 Glob 找 `FI-012*`。

### 2. 用問答深入

可問的如下。**不必全問，挑對這個 ID 最有用的 2〜3 個**。
能列出選項的用 `AskUserQuestion`。

- **升級條件 / 不採用條件** — `⚠️` 就問「發生什麼會變 ✅」；`✅` 就問「發生什麼會掉到 ❌」
- **實作入口** — 最先要動哪個檔案、函式
- **影響範圍** — 有無破壞性變更、遷移策略
- **比較對象** — 類似 OSS 或自己過去專案的決定
- **驗證方式** — 怎麼判斷「成功了」

**處理外部事實（其他工具的功能、benchmark 數字）時，當場用 WebSearch / WebFetch 查證並留 URL。**
不要憑記憶寫。查不到就明寫「未確認」。
vault 是長期參考的資產，而且點子的性質讓它事後很少被驗證。這裡混進的錯誤會留很久。

### 3. 判斷留在行內或升級

標準見 [`evaluation.md`](evaluation.md)。簡單說，1 行（〜80 字）寫得完就只更新備註。
需要論點、條件分支、多個 URL、程式片段就升級為詳細檔。

### 4. 保存

**行內就夠時**：用 Edit 更新 index 表格該行。備註可以**覆寫**成最新的一行摘要。

**升級為詳細檔時**：

1. Write `<feature-ideas>/FI-NNN.md`（已存在就用 Edit 追加）。frontmatter 與內文格式依
   [`evaluation.md`](evaluation.md) 的「詳細檔格式」
2. **討論結果帶日期追加到 `## 判定歷程`**（不堆在備註）
3. index 備註換成「一行摘要 + 詳細檔連結」
4. index 狀態改 `probing`
5. 詳細檔的 `updated` 改成今天

**出現日期型期限時**（「N 週後重新評估」等）：

- 能換成日期就在 vault 的 `## 重新評估佇列` 加一行。
  **一定要寫 `要判定什麼`**（只有日期的期限，到了也不知道要決定什麼，就會爛掉）
- 像「出現〜時」「驗證〜之後」這種**只能靠外部條件判斷的，不寫進 vault**。
  依 [`archive.md`](archive.md) 的「隔離條件觸發事項」移到 `known-issues.md` 等

### 5. 回報

- 深入結果的重點 3〜5 行
- 更新過的檔案路徑
- 下一步選項（繼續 `discuss` / 若有 `superpowers:writing-plans` 就進設計階段 / 先擱置）

**不要擅自進入實作階段。** 列出選項，等使用者選。

## 不要做的事

- **擅自改 ID / 開新 ID** — `discuss` 只深入既有的一項
- **在備註堆帶日期的歷程** — 追加位置是詳細檔的 `## 判定歷程`
- **在 `<feature-ideas>/` 用別的命名建詳細檔** — 底下只能是 `FI-` 開頭的名稱
- **在詳細檔寫實作計畫（`- [ ] Step N` 形式的步驟）** — 那是 `docs/plans/` 的工作。
  放進 vault 目錄，累積下來 vault 的計數指標就不可信
