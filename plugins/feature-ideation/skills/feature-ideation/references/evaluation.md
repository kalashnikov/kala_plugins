## 評估軸的意義

評估是**同一專案內的相對比較**，不是絕對標準。

| 軸 | 值 | 意義 |
|---|---|---|
| 效益 | **大** | 使用者感受明顯改變。核心指標（搜尋準確度、處理速度等）有數字變化 |
| 效益 | **中** | 好用程度提升、痛點減少 |
| 效益 | **小** | 有了方便，沒有也不困擾 |
| 難度 | **低** | 不到 100 LOC / 半天〜1 天 |
| 難度 | **中** | 數百 LOC / 數天 |
| 難度 | **高** | 有設計議題 / 1〜2 週 |
| 難度 | **極高** | 研究性質 / 以月計 / 侵入既有架構 |
| 限制 | **✅** | 不違反專案不變條件（value prop / 非目標） |
| 限制 | **⚠️** | 有條件可採用。**一定要在備註寫升級條件** |
| 限制 | **❌** | 不採用候選。為了省下討論，只留紀錄 |

**為什麼限制很重要**：專案大多有「不做 XX」的不變條件（維持單一執行檔、不依賴外部服務、可離線運作等）。
破壞它的提案再好也不會被採用。及早標記，討論精力才能集中在可採用的範圍。

**`⚠️` 的寫法**：讀不出「怎麼處理就能升為 ✅」就無法討論。
要寫出**升級路徑**，例如「伺服器自己呼叫 LLM 就是 ❌，前處理改走 hook 就是 ✅」。

**只寫 `效益 大` 卻沒理由的項目價值很低**。在備註加一行「為什麼這樣評」
（例：「官方數據失敗率改善 35-50%」）。但外部數字**要當場查證並留 URL**（不要憑記憶寫）。

## 容易看錯難度的情況

- **看起來「只是加在既有功能上」，其實有設計議題** — 加入既有抽象沒預想到的軸時，
  實作小但設計重。拿不準就往上調一級
- **牽涉外部依賴** — 加函式庫即使程式碼量是零，也要評估授權、維護狀況、執行檔大小
- **「之後改不回來」的** — 資料格式、公開 API、檔案配置的變更，LOC 再小也當高難度處理

## 把範圍寫法收斂成單一值（遷移時）

舊 vault 可能混有 `中〜大`、`小〜中`、`低〜中` 這類範圍寫法。
新格式的統計假設單一值，所以要收斂，但**收斂方向不一致，之後就看不懂**。

> **效益往下收，難度往上收。** 這是不膨脹期望值的一側，
> 也和上面「難度拿不準就往上調」方向一致。

若往相反方向收，**只在那一行留下理由**。把收斂一覽放在 vault 圖例下方或
`## 變更紀錄`，之後可以逐行驗算。

同樣的範圍寫法（例如 2 行都是 `中〜大`）被收成不同方向卻沒寫理由，
讀的人無法判斷哪邊錯。**同樣輸入得到不同輸出的地方一定要記錄。**

## 備註：留在行內，還是升級為詳細檔

index 的備註欄原則上**保持簡短**。越討論越長，用以下標準判斷。

### 留在行內即可

- 1 行（〜80 字）寫得完評估依據
- `⚠️` 的升級條件一行寫得完
- 只有一個比較對象 + 簡短參考

### 升級為詳細檔 `FI-NNN.md`

符合任一就切出去。

- 需要寫多個論點 / 條件分支
- 想放多個引用 / URL
- 包含程式片段或設定範例
- `discuss` 討論的結果有 3 段以上
- 寫在行內會超過 **200 字**

升級後，index 備註換成「一行摘要 + 連結」，狀態改 `probing`。

## 評價變動時追加到詳細檔的判定歷程

「為什麼現在是這個評價」，要看**評價變動的歷程**才知道。直接覆寫，將來會再討論一次同樣的事。

但**追加位置不是 index 的備註**。在備註堆帶日期的追加，即使已有詳細檔，
index 的格子也會膨脹（實際曾達 1,200 字）。「200 字以內」與「不刪歷程」
要把追加位置分開才能同時成立。

- **index 的備註**：永遠只有**最新的一行摘要 + 連結**。可以覆寫
- **詳細檔的 `## 判定歷程`**：只能追加。帶日期，新的在上

```markdown
## 判定歷程

- **2026-07-25**: 確定 NO-GO。門檻是預想的 3 倍，訊號 4 不成立
- **2026-05-18**: 細分為 Phase 2-pre / 2-main。訂出 GO 訊號 4 項 + NO-GO 3 項
- **2026-05-03**: 登錄。⚠️（前處理放哪裡未定）
```

還沒有詳細檔時評價就變了，那就在那時切出詳細檔。

## 詳細檔格式

`<feature-ideas>/FI-NNN.md`（或 `FI-NNN-<slug>.md`）。多個點子合併時用 `FI-006+FI-009-<slug>.md`。

```markdown
---
id: FI-012
title: "<一行標題>"
status: probing        # 與 index 的狀態一致
created: YYYY-MM-DD    # 建立此檔的日期
updated: YYYY-MM-DD    # 每次動內容就更新
category: "<index 的標題名>"   # 選填
related:                          # 選填。相對路徑
  - ../plans/<...>.md
---

# <title>

## 一句話
<1〜3 行。貼到 index 備註的就是這段摘要>

## 背景 / 起因
<為什麼登錄。外部事實一定附 URL>

## 論點
<選項 A/B/C、條件分支、取捨>

## 採用條件 / 不採用條件
<發生什麼就變 ✅ / ❌>

## 判定歷程
<只能追加。帶日期，新的在上>

## 未解決的問題
- [ ] <下一個讀的人最先要回答的問題>

## 參考
```

- `updated` 是讓 `check` 找出「研究了卻沒判定」項目的訊號。
  檔案 mtime 會作為佐證，所以忘了更新也只是降級運作
- `id` / `status` 是 index 的副本。**以 index 為準**，不一致由 `check` 回報
- 不放 `tags`（會冒出 skill 用不到的標籤）。用 Obsidian 的專案可自行加
- **不要把「與既有文件的分工」表複製到詳細檔**。分工只由 vault 本體負責
- 建子項目時用 `FI-012-a` 這樣**加上父 ID 前綴**。不單獨使用局部 ID（`R-1` 等）。
  子項目超過 10 個，那就不是一個點子而是計畫，拆成多個 `FI-` 或移出 vault
